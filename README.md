# Python Failed Login Detector

A beginner-friendly cybersecurity project that analyzes **fictional** login records, counts failed login attempts by IP address, and flags IP addresses that match two simple brute-force-style patterns. It produces a readable text security report.

> **Educational use only.** This tool works on made-up sample data. It does not monitor live systems, read real logs, or detect real attackers. See [Educational-Use Disclaimer](#educational-use-disclaimer).

## Features

- Counts failed login attempts **per IP address**
- Flags IPs with **5 or more failed attempts** (Rule 1)
- Flags IPs with failed attempts against **3 or more unique usernames** (Rule 2)
- Ignores successful logins when counting failures
- Validates every record and **skips malformed ones safely** (missing fields, invalid IPs, unknown statuses, wrong data types), listing each skipped record in the report
- Handles **empty input** without crashing
- Normalizes data (case and whitespace in usernames and statuses) so `Admin` and `admin ` count as one username
- Saves a readable report to `failed_login_security_report.txt`
- Includes **27 automated tests** using Python's built-in `unittest`

## How the Detection Rules Work

The program reads each login record (IP address, username, status) and keeps only `FAILED` records for detection. For every IP address it tracks two numbers: how many failures it caused, and how many different usernames those failures targeted.

| Rule | Name | Condition | Why it matters |
|------|------|-----------|----------------|
| 1 | Repeated failed logins | 5 or more failed attempts from one IP | Many failures from one source can indicate password guessing (brute force) |
| 2 | Multiple usernames targeted | Failed attempts against 3 or more different usernames from one IP | Trying many accounts can indicate account enumeration or password spraying |

An IP can trigger one rule or both. The thresholds are set at the top of `failed_login_detector.py` (`FAILURE_THRESHOLD` and `USERNAME_THRESHOLD`) so you can experiment with them.

**What counts as a malformed record?** A record is skipped (and listed in the report) if it is not a dictionary, is missing `ip`, `username`, or `status`, has an empty or non-text value, has an invalid IP address (such as `999.1.1.1`), or has a status other than `SUCCESS` or `FAILED`.

**Sample data design.** The built-in fictional dataset includes an IP with exactly 5 failures (Rule 1 only), an IP with 3 failures against 3 usernames (Rule 2 only), an IP that triggers both rules, an IP with 4 failures (just under the threshold, not flagged), normal successful logins, and 4 deliberately malformed records. IP addresses come from ranges reserved for documentation, so they are not real hosts.

## Installation and Execution (Windows)

### 1. Install Python

1. Download Python 3 from <https://www.python.org/downloads/>.
2. Run the installer and **tick "Add python.exe to PATH"** before clicking *Install Now*.
3. Open **Command Prompt** or **PowerShell** and check the installation:

```
py --version
```

### 2. Get the project

Either download the ZIP from GitHub (**Code → Download ZIP**) and extract it, or clone it with Git:

```
git clone <YOUR-REPOSITORY-URL>
```

### 3. Open the project folder

```
cd Python-Failed-Login-Detector
```

### 4. Install dependencies

No external packages are needed. You can still run this command; it will finish without installing anything:

```
py -m pip install -r requirements.txt
```

### 5. Run the program

```
py failed_login_detector.py
```

The report prints in the terminal and is saved as `failed_login_security_report.txt` in the project folder.

### 6. Run the tests

```
py tests.py
```

If `py` is not recognized, try `python` instead.

## Limitations

- Uses **fictional sample records only**; it does not read real log files
- Does **not** monitor live systems or detect real attackers
- Has **no time window**: failures spread over days are counted together
- Uses **fixed thresholds**, which can cause false positives (e.g., a user mistyping a password) and false negatives (e.g., an attacker staying under the limit)
- Does not use IP reputation, geolocation, or account-lockout data
- Treats each IP separately, so attacks spread across many IPs are not correlated
- An alert is a lead for human review, **not proof** of malicious activity
